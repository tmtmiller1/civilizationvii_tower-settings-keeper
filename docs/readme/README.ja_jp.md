# Tower Settings Keeper

Civilization VII用のModです。導入すると、ほかのModで行った設定がゲームを再起動しても保持されます。このMod自体には設定項目がなく、ゲームプレイも変わりません。

## 問題

Modは設定をゲームの`localStorage`に保存します。Civilization VII 1.5.0では、この保存領域に不具合があります。読み取りを行うと、どの項目を要求したかに関係なく、保存領域の最初の項目が返されます。項目の一覧を取得する方法もありません。そのため、Modが自分の設定を読み取れるのは、自分の項目がたまたま先頭にある場合だけです。それ以外のModは別のModのデータを受け取り、それを自分のものとして扱い、次に保存するときに自分の名前で書き戻してしまいます。

プレイヤーから見ると、オプション画面が起動のたびにリセットされ、ときにはあるModの設定が別のModの中に現れます。

多くのオプション画面は`modSettings`という1つの項目を共有し、Modごとに区画を持っています。さらに、Workshopのおよそ50個のModには、2つ目の項目を見つけると保存領域全体を消去する補助コードが含まれています。設定を自分専用の項目に保存するModが1つあるだけで、次の保存時にほかのすべてのModの設定が消えてしまいます。

## このModの動作

すべての項目を、ゲームが正しく読み取れる唯一の行の中に保持し、`localStorage`へのあらゆる呼び出しにその行から応答します。

- 独自のキーを使うModは、そのキーで保存され、そのキーで読み戻されます。
- 共有項目`modSettings`はこれまでどおり、Modごとの区画として機能します。既存のオプション画面に変更は不要です。
- 保存領域は常に1つの項目だけを報告するため、消去の補助コードは決して実行されません。
- ほかのModがすでに保存領域の順序を乱している場合、このModは識別できる項目を正しい位置に移し、それ以外には手を触れません。起動のたびに再確認します。

ほかのModを更新する必要はありません。WorkshopにすでにあるModとそのまま動作します。

## すべてのModで動作し、変更は不要

このModは、設定を保存するすべてのModについて、そのModを現状のまま問題を解決します。Mod作者は何も変更する必要がなく、登録も不要です。このModを導入したプレイヤーは、手持ちのすべてのModで設定が一度に正しく機能するようになります。

Mod作者にはもう1つの選択肢があります。同じファイルを自分のModに同梱すれば、プレイヤーがこのModを導入しなくても保護されます。詳しくは下の「Mod作者の方へ」を参照してください。ファイルを同梱したModとこのModは同時に導入できます。動作するのは最新の1つだけで、残りは何もしません。

## インストール

Steam Workshopでサブスクライブするか、最新リリースのzipをダウンロードして`~/Library/Application Support/Civilization VII/Mods/`（macOS）または`%LOCALAPPDATA%\Firaxis Games\Sid Meier's Civilization VII\Mods\`（Windows）に展開してください。その後、「追加コンテンツ」で有効にします。設定することは何もありません。

## 知っておきたいこと

- これから保存する設定は保持されます。このModを導入する前に失われた設定は戻りません。ただし、このModが識別できる項目としてディスクに残っている場合は別です。
- 保存領域がすでに壊れていた場合、このModは識別できない項目をどのModが書いたのか推測しません。その項目が唯一残っているものであれば、それを中心に保存領域を再構築し、内容を保持します。項目の名前は失われます。内容を認識できる後のバージョンが、正しい名前に戻します。そうした項目が2つ以上前にある場合は、それらの手前に新しいルートを作り、それらはディスクに残したまま、次の起動時に再度試みます。ほかのModのデータを上書きすることは決してありません。
- ゲームはModスクリプトの実行順序を保証しません。スクリプトの読み込み時点、つまりこのModが実行される前に設定を読み取るModは、その起動に限り従来の動作になります。これまでのテストではすべての起動でこのModが最初に実行されました。
- このMod自身のテキストは、ゲームが対応する11の言語すべてに翻訳されています。
- ストレージには4 MBのサイズ上限があります。これは28個のModが使う0.5 MBの8倍です。これを超えようとするModは、その1回の書き込みだけが拒否されて以前の設定を保持し、「オプション、アドオン」にそのModの名前を示す「ストレージの上限に達しました」の行が表示されます。他には何も影響しません。下の「負荷と上限」を参照してください。
- 画面には何も表示されません。例外は`Logs/UI.log`の`[settings-keeper] ready:`で始まる1行と、上で説明した予備配置の場合です。その場合は「オプション、アドオン」に「ストレージを再構築」の行が表示されます。それを押して確認すると、識別できなかった項目が削除され、保存領域が1つの項目として書き戻されます。保存領域が正常に戻ると、この行は消えます。

## 負荷と上限

すべてが1つの行に収まるので、注意すべきはその行のサイズです。テスト機では、28個のModを入れた状態で行は約0.5 MBで、ほぼ全部が1つのModのゲーム履歴です。オプションパネル1つが足すのは数百バイトです。書き込みは行全体をシリアライズし、このサイズで約8 msかかりますが、1つのタスクにつき1回だけで、そこで書く値の数は関係ありません。Modの数そのものは問題ではなく、どれだけ保存するかが問題です。

エンジンがどこで限界を迎えるかを調べるため、同じ28個のModを入れた「今すぐプレイ」のゲームで、プローブがこのModを通して行を1 MBずつ大きくし、別の起動でそれぞれの要素を単独でも試しました。

| 行のサイズ | 1回の書き込み（シリアライズと保存） | 書き込み後の1キーの読み取り |
|---|---|---|
| 0.5 MB、実際のストア | 8 ms | 2 ms |
| 5 MB | 71 ms | 20 ms |
| 10 MB | 101 ms | 64 ms |
| 13 MB | 141 ms | 67 ms |
| 16 MBを1回で書き込み | 102 ms | |
| 20 MB、1 MBずつ増加 | 197 ms | |

どのサイズでも失われたり壊れたりしたものはなく、ストレージは終始1行のままでした。上限があるのはゲームのプロセス自体です。行を連続して何度も読み込んで書き直した場合は14 MBの段階で、書き直すだけの場合は21 MBの段階で、クラッシュレポートを残さずに停止しました。14 MBのストアはメインメニューでもゲーム内でも読み込め、すべてのキーが読めましたが、行をもう一度読み直して書き直すと停止しました。停止時のプロセスは1.9 GBを使っていたので、上限はストレージではなくゲームのメモリです。

そのため、このModは行を4 MBより大きくする書き込みをすべて拒否します。これはゲームが停止した最小サイズの4分の1です。拒否された書き込みは、ブラウザのlocalStorageが満杯のときに投げられるのと同じ`QuotaExceededError`を投げるので、Web API向けに書かれたModはその意味をすでに知っています。そのModの以前の値は残り、他のModには触れず、ログがModの名前とサイズを記録し、「オプション、アドオン」に同じ内容と、それを消すOKを備えた「ストレージの上限に達しました」の行が表示されます。上限は`ui/settings-keeper.js`の先頭にある1つの定数です。

## Modの削除

通常は何もする必要がありません。保存領域は1行なので、ゲームは以前と同じく`modSettings`を最初に読み、ほかのModは自分の区画を見つけます。追加されているのは、ほかのModが無視する内部フィールドだけです。「オプション」に「ストレージを再構築」の行が表示されている場合は、このModを無効にする前にそれを押してください。そうしないと、ほかのModの消去補助コードが次の保存時に保存領域を消してしまいます。

## Mod作者の方へ

何も求められません。あなたのModが共有項目`modSettings`を使っていても、独自のキーを使っていても、このModが導入された環境で設定は正しく機能します。

プレイヤーがこのModを導入しなくても保護されるようにしたい場合は、この修正を自分のModに同梱できます。ファイル1つとmodinfoの2行だけで、設定のコードはそのままです。手順は[embed/README.md](../../embed/README.md)（英語）にあります。最新リリースの`settings-keeper-embed-<version>.zip`を使うこともできます。
